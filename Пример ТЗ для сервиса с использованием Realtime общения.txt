Техническое задание
Голосовой AI-администратор ресторана на Realtime API
1. Цель проекта
Разработать учебное веб-приложение — голосового AI-администратора ресторана, способного в реальном времени разговаривать с гостем, проверять наличие свободных столиков и создавать бронирования.
Приложение разрабатывается с помощью Codex в две последовательные итерации.
Итерация 1. Голосовой AI-администратор в браузере
Создать локальное веб-приложение, в котором пользователь разговаривает с AI через микрофон компьютера.
Подключить три голосовых Realtime-решения через API:
OpenAI Realtime API.
Google Gemini Live API.
ElevenLabs Eleven Realtime API.
Предусмотреть переключение между ними для сравнения естественности русского голоса, скорости ответа, понимания речи и качества диалога.
Все решения должны работать с одной учебной базой столиков и бронирований.
Итерация 2. Телефонный AI-администратор
Расширить готовое приложение, подключив Voximplant для приёма настоящих телефонных звонков.
Гость звонит на тестовый номер, разговаривает с AI-администратором и может забронировать столик.
Телефонный оператор должен использовать ту же базу данных и функции бронирования, что и веб-приложение.
Для учебной демонстрации не требуется подключение к настоящему ресторану, платёжным системам, CRM или отправке уведомлений.
Важно: разработку начинать только с итерации 1. Переход к итерации 2 разрешён исключительно после проверки первой итерации пользователем и его явной команды.

2. Итерация 1. Голосовой AI-администратор
2.1. Пользовательский интерфейс
Создать современное веб-приложение с возможностью локального запуска на компьютере.
На главной странице разместить:
Название «Голосовой AI-администратор ресторана».
Переключатель провайдера: OpenAI, Gemini, ElevenLabs.
Кнопку «Начать разговор».
Кнопку «Завершить разговор».
Индикатор состояния голосового соединения.
Индикаторы «AI слушает», «AI отвечает», «Проверка бронирования».
Текстовую историю разговора.
Панель с распознанными параметрами бронирования.
Результат проверки свободных столиков.
Статус создаваемой брони.
Дополнительно предусмотреть раздел «Расписание ресторана», в котором отображаются столики, занятые интервалы и созданные бронирования.
Интерфейс должен работать в браузере на локальном компьютере.
При переключении голосового провайдера текущий разговор завершается, после чего можно начать новую сессию с выбранным решением.
2.2. Подключение Realtime-моделей
Реализовать прямое API-подключение трёх голосовых решений.
OpenAI Realtime API
Использовать доступную актуальную модель семейства GPT Realtime, поддерживающую:
двусторонний голосовой диалог;
потоковую передачу аудио;
обработку перебиваний;
вызов инструментов приложения;
инструкции для ведения разговора.
Google Gemini Live API
Использовать актуальную модель Gemini с поддержкой Live API, голосового диалога и вызова функций.
ElevenLabs Eleven Realtime API
Использовать Eleven Realtime, предпочтительно модель eleven_realtime_v1_max, при условии её доступности в API.
Подключение выполнять непосредственно из приложения через API. Создание отдельного агента в кабинете ElevenAgents не требуется, если выбранный Realtime API предоставляет необходимые возможности.
Если указанная версия модели недоступна или изменилась, Codex должен проверить официальную документацию и выбрать совместимую актуальную Realtime-модель, сообщив об изменении.
Для каждого провайдера реализовать отдельный программный адаптер, но сохранить общие правила разговора и бронирования.
Требования ко всем трём решениям:
голосовой диалог на русском языке;
передача аудио в реальном времени;
потоковое воспроизведение ответа;
естественные короткие реплики;
определение окончания речи пользователя;
возможность прерывать ответ агента;
вызов функций проверки и создания брони.
Использовать официальные API и поддерживаемые механизмы интеграции каждого провайдера.
2.3. Realtime, Streaming, WebSocket и WebRTC
Реализовать живой голосовой диалог без обязательной предварительной записи отдельных аудиофайлов.
Звук с микрофона должен передаваться выбранному голосовому решению непосредственно в ходе разговора.
Голосовой ответ AI должен начинать воспроизводиться по мере поступления аудиоданных, не дожидаясь завершения всего ответа.
Для связи использовать подходящий транспорт:
OpenAI Realtime — WebRTC или WebSocket;
Gemini Live — WebSocket;
Eleven Realtime — WebSocket, если это предусмотрено выбранным API.
Для браузерного голосового соединения с OpenAI предпочтительно использовать WebRTC, если он упрощает обработку аудио и обеспечивает стабильную работу.
Не требуется искусственно переводить все три интеграции на один транспортный протокол.
Поддержка перебиваний
Пользователь должен иметь возможность начать говорить, пока AI произносит ответ.
Например:
AI: «На двоих у нас есть столик на...»
Гость: «Нет, нас будет четверо».
В этом случае приложение должно:
Прекратить воспроизведение предыдущего ответа.
Передать новую реплику выбранному голосовому решению.
Обновить количество гостей.
При необходимости повторно проверить наличие свободного столика.
После перебивания непроигранная часть отменённого ответа не должна продолжать звучать.
2.4. Сценарий голосового разговора
AI выполняет роль вежливого администратора учебного ресторана.
В начале разговора он приветствует гостя и предлагает помочь забронировать столик.
Для оформления бронирования необходимо получить:
дату посещения;
время;
количество гостей;
имя гостя;
пожелания, если они есть.
Телефонный номер и адрес электронной почты не требуются.
Агент должен:
задавать вопросы по одному;
не повторять уже полученные сведения;
понимать разговорные формулировки;
учитывать изменения, внесённые гостем;
уточнять неоднозначные сведения;
не придумывать свободные столики;
не обещать выполнение пожеланий без подтверждения.
Если гость говорит «завтра» или «в следующую пятницу», агент должен определить конкретную дату по часовому поясу ресторана.
Создание брони на прошедшую дату или время запрещено.
Перед созданием бронирования агент озвучивает дату, время, количество гостей и имя, затем спрашивает явное согласие гостя.
2.5. Учебная база данных ресторана
Использовать SQLite — локальную SQL-базу данных, которая не требует отдельного сервера.
Создать две основные таблицы.
Таблица tables — столики
Поля:
id — идентификатор;
table_number — номер столика;
capacity — вместимость;
features — дополнительные характеристики столика.
Таблица reservations — бронирования
Поля:
id — идентификатор брони;
table_id — идентификатор столика;
reservation_date — дата;
reservation_time — время;
duration_minutes — продолжительность;
guest_count — число гостей;
guest_name — имя;
wishes — пожелания;
status — статус;
source — источник бронирования: OpenAI, Gemini, ElevenLabs или телефонный звонок.
Учебные параметры ресторана:
Часы работы: 12:00–23:00.
Продолжительность бронирования: 90 минут.
Два столика на 2 человека.
Один столик на 4 человека.
Один столик на 6 человек.
Часовой пояс задаётся в настройках ресторана.
Заполнить базу несколькими тестовыми бронированиями, чтобы были как свободные, так и занятые интервалы.
Приложение должно учитывать вместимость столиков, часы работы и пересечения интервалов бронирования.
Бронирование не должно выходить за пределы часов работы ресторана.
Данные должны сохраняться после перезапуска приложения.
Все голосовые провайдеры используют одну базу SQLite.
2.6. Функции бронирования
Реализовать три функции backend.
check_availability
Проверяет доступность столиков на заданную дату и время для указанного количества гостей.
Возвращает результат проверки и подходящие свободные столики.
find_alternative_slots
Если подходящего столика на запрошенное время нет, предлагает ближайшие доступные интервалы из учебного расписания.
create_reservation
Создаёт бронирование после явного подтверждения гостя.
Перед сохранением повторно проверяет доступность столика.
При успешном создании возвращает идентификатор бронирования.
Если место уже занято, возвращает ошибку и не создаёт бронь.
Одна подтверждённая операция не должна создавать две одинаковые брони, в том числе при повторном вызове функции.
Для всех трёх голосовых решений реализовать вызов этих функций через поддерживаемые API-механизмы вызова инструментов.
Обязательные правила:
AI не может самостоятельно объявлять столик свободным без проверки.
Бронь создаётся только после явного согласия гостя.
Перед записью выполняется повторная проверка доступности.
Подтверждение брони произносится только после успешного сохранения в SQLite.
Если время занято, предлагается альтернатива.
Пожелания записываются, но не считаются гарантированными.
Повторный вызов создания той же подтверждённой брони не должен создавать дубликат.
2.7. Завершение разговора
После успешного оформления агент сообщает:
имя гостя;
дату;
время;
количество гостей;
подтверждение бронирования.
Если гость отказался или завершил разговор до подтверждения, новая бронь не создаётся.
При нажатии «Завершить разговор» приложение прекращает работу микрофона, воспроизведение аудио и соединение с голосовым провайдером.
Созданные бронирования остаются в базе.
2.8. Сравнение трёх Realtime-решений
Реализовать возможность последовательно провести одинаковые голосовые диалоги с OpenAI, Gemini и ElevenLabs.
Для каждого решения использовать одинаковую роль администратора, одинаковые правила бронирования и общую базу данных.
Для сопоставимого тестирования предусмотреть возможность восстановить исходные учебные бронирования между тестами.
Сравнивать:
Естественность русского голоса.
Правильность произношения и интонации.
Скорость начала голосового ответа.
Качество понимания речи.
Способность обрабатывать перебивания.
Соблюдение сценария бронирования.
Ориентировочную стоимость использования API.
Предусмотреть простую таблицу сравнения в интерфейсе, в которую преподаватель может вручную вносить оценки и комментарии.
Автоматически измерять все показатели необязательно.

3. Итерация 2. Подключение Voximplant
3.1. Цель
Добавить возможность общаться с голосовым AI-администратором через обычный телефонный звонок.
Использовать Voximplant для приёма и маршрутизации звонков.
Телефонный агент должен использовать готовую логику бронирования и общую SQLite-базу из первой итерации.
3.2. Подключение телефонии
Настроить:
аккаунт Voximplant;
тестовый номер или другой поддерживаемый маршрут входящего звонка;
сценарий обработки вызова;
соединение с голосовым AI;
обращение к backend приложения для проверки и создания брони.
Для телефонной демонстрации достаточно подключить один голосовой движок — OpenAI Realtime API.
Не требуется подключать к Voximplant все три решения, которые сравнивались в первой итерации.
Использовать поддерживаемую Voximplant интеграцию с OpenAI Realtime, если она совместима с выбранной моделью.
Если интеграция передаёт телефонное аудио напрямую между Voximplant и голосовой моделью, приложение должно продолжать обслуживать вызовы функций бронирования и хранить данные.
Не разрабатывать собственный аудиомост, если готовая интеграция решает эту задачу.
3.3. Сценарий телефонного звонка
Гость звонит на тестовый номер.
Voximplant принимает вызов.
Гость слышит приветствие AI-администратора.
Агент уточняет дату, время, количество гостей и имя.
Проверяет свободный столик через общий backend.
Если время занято, предлагает альтернативу.
После явного согласия гостя создаёт бронирование.
Подтверждает результат голосом.
Бронирование появляется в общей базе и интерфейсе приложения.
Во время телефонного разговора также должна поддерживаться возможность перебивания агента.
Каждый новый звонок должен начинаться с отдельной историей разговора.
3.4. Локальная работа и публичное подключение
На первой итерации приложение работает локально, без аренды сервера.
Для второй итерации обеспечить доступ Voximplant к необходимым backend-функциям через защищённый публичный адрес.
Допускается использовать Cloudflare Tunnel или аналогичный инструмент.
Использовать HTTPS и WSS там, где это необходимо для выбранной интеграции.
На этапе учебной демонстрации аренда VPS не обязательна.
Компьютер, backend и туннель должны оставаться включёнными во время телефонного звонка.

5. Проверка готового приложения
Итерация 1 считается выполненной, если:
Приложение запускается локально в браузере.
Можно начать голосовой диалог через микрофон.
Работает выбор между OpenAI, Gemini и ElevenLabs.
Все три решения поддерживают потоковый голосовой разговор.
Гость может перебить AI и скорректировать свои данные.
Агент проверяет наличие столика в SQLite.
При занятом времени предлагает альтернативу.
Только после согласия гостя создаёт одну бронь.
Созданная бронь сохраняется и отображается в интерфейсе.
Можно сравнить три голосовых решения на одинаковом сценарии.
Итерация 2 считается выполненной, если:
Можно позвонить на подключённый тестовый номер.
На звонок отвечает AI-администратор.
Агент поддерживает естественный голосовой диалог.
Гость может перебивать ответ агента.
AI проверяет доступность столика через общий backend.
После подтверждения создаёт бронирование.
Бронь появляется в той же базе, которая используется веб-приложением.

6. Ограничения учебного проекта
Не требуется реализовывать:
настоящую ресторанную CRM;
отправку SMS и электронных писем;
оплату бронирований;
личные кабинеты;
сложную систему авторизации и ролей;
промышленный мониторинг;
автоматическое восстановление длительных звонков после обрыва;
поддержку большого числа одновременных звонков;
промышленную систему записи и хранения телефонных разговоров.
Сохранить только обязательную обработку ошибок:
ошибка подключения к голосовому API;
невозможность проверить наличие столика;
ошибка сохранения брони;
корректное завершение голосового сеанса;
защита от двойного бронирования.
При ошибке проверки или сохранения AI должен сообщать, что бронирование не подтверждено.
Обрыв соединения и отсутствие ответа гостя не считаются согласием на создание брони.

Итерация 2 — только после разрешения пользователя
Приступать к подключению Voximplant только после явной команды пользователя о начале второй итерации.
До получения этой команды:
не подключать Voximplant;
не настраивать телефонию и телефонные маршруты;
не создавать телефонные сценарии;
не запрашивать ключи и доступы Voximplant;
не запускать работы по второй итерации.
После разрешения пользователя:
Проверить готовность аккаунта и телефонного маршрута Voximplant.
Настроить подключение OpenAI Realtime к телефонному вызову.
Предоставить защищённый доступ к backend бронирований.
Связать телефонный сценарий с общей SQLite-базой.
Проверить реальный входящий звонок и создание брони.
Вторая итерация должна развивать существующее приложение, сохраняя общий backend, базу данных и логику бронирований.
Главное правило для Codex: сейчас необходимо полностью реализовать только итерацию 1, предоставить приложение для тестирования и выполнять необходимые исправления. К итерации 2 переходить исключительно по отдельному прямому указанию пользователя. Самостоятельно начинать вторую итерацию запрещено.
